# R189｜解决Web游戏首屏16份人物模型全量等待：真开局手牌优先、真实GLB后台验证、下一回合零假模型

2026-11-19。阶段重点是**首屏变快、第一次出牌不卡、手机不OOM**；不增加美术精度、不再升级高清猫头鹰。仅隔离的QA研发分支。旧R147、GitHub main和真正玩家默认行为**未改动**。实测代码的游戏规则、16位原有模型身份、60张牌、46种法术均不降级。

## A. 源代码已实际重构（不是规划）

1. summon-models.mjs 的模型导入器新增严格的真实GLB身份子集参数；原始默认仍是完整12/12。每个候选GLB必须通过 GLTFLoader、真实边界、尺寸、网格检查才算完成。完全不创建任何粗模占位。
2. scene.mjs 从父页面实际 seed / deck 获取确定性两方开局手牌，通过同一条 engine.createGame() 规则找出必须存在的召唤物。以种子173经典卡组为例，开局双方真正需要T04/T01/E02/E04/M01/G03这6个GLB，另外E01/G01和双方发牌角色使用原4份真实VRM。**首次可玩先验证这10份**，不必等后续6个与第一轮无关的GLB。
3. 首屏真实三维、体育馆、模型可操控并显示后再启动剩余GLB后台任务。实际模型以异步 onPrototype 回执逐个进入同一真正的Map。严格限制身份、禁止重复，最后必须最终满足全16/12召唤GLB身份；若异常立即对家长/玩家停止出牌而非显示空角色。
4. game.mjs 的卡牌输入逐个验证真实GLB已到位，未到位的卡不可出牌并显示真实状态；桌面场景以原始3D角色实际出现，绝不假装已经加载。切换牌组在后台未完成前禁用，全部就绪后恢复。
5. **最关键：没有把等待挪到“结束回合”。** 现在通过真实游戏状态的 structuredClone+endTurn+aiTurn 做一遍无副作用的确定性对手下一回合模拟。只检查对手实际即将打出的角色是否有真GLB；如果都准备好，原先后台未全部完成也可以真正结束回合、让AI真实打牌。没有准备好的极少数角色才暂时禁用该次操作，并给出明确提示；预测异常则严格拒绝。
6. QA参数：qa=1&r189Stream=on 启动本次实验。没有这个参数时原始16/16准备门槛完全不变。BG并发4、无额外启动等待，单独参数r189BgConcurrency和r189BgDelay可复现实验。原来的R188 BarnOwl轻量带4段原生动作的候选依然是QA独立开关，不混淆不同改造贡献。

### 后台解析耗时——不隐瞒成本

- 并发4的桌面后台模型全部验证：**875–2744ms**（3次）；移动视口CPU×4：**1885–5071ms**（2次）。背景资源仍需要时间，而且波动很大。
- 并发2的桌面后台耗时约**6795–7464ms**；并发3约**5083–5393ms**。这些没有带来更可靠的首屏/卡顿综合效果，不当默认方案。
- 一次原始并发1实验约**9161ms**，明显不值得。**R189使用并发4仅是QA里当前较好候选。**
- 后台没有额外强行GPU预热所有模型，维持R188已找到的真实轻量猫头鹰。观察到的长任务仍因调度、GPU和设备而异，不能以没有记录到LongTask当作绝对零卡顿。

## D. 资源与上线限制

R189在初始阶段减少的是**必须阻塞首屏的解析/载入资源**，不是减少全部匹配结束时的GPU峰值。后台会逐渐补齐全部模型；如果三星手机显存本就装不下，R189本身不会神奇解决OOM。R188替换巨型原猫头鹰能减少初次下载与纹理预算，但全局峰值仍应进一步测量。

真机三星S22 Agent此轮仍未在线，无法验证Android GPU、VRAM、上下文丢失与热状态稳定性；**430×900移动视口是Z890 RTX桌面GPU＋CPU限速4倍，不能声称真机已经通过**。真实游戏在玩家可以出牌后仍可能有后台加载，必须继续测总耗时、各平台内存峰值和整个战斗周期，不能只看首屏数字。
