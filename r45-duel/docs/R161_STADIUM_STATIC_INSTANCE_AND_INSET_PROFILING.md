# R161｜Web 3D 战斗卡顿：体育馆静态实例化 + 双相机实测

**状态：独立 Draft QA 分支，未合并 / 未上线，R147 正式默认不变。**

## 目标与画质硬门槛

在不改变任何人物、卡牌、纹理分辨率、PBR 材质、骨骼、粒子、声音、主视角、动画速度的情况下减少可证明的 GPU 绘制提交。禁止为提升 FPS 擅自关闭特写、降低清晰度或缩减角色。

## 本轮可验证的静态几何优化

`scene/stadium.mjs` 原本为完全静止的 3D 天花灯箱、桁架、立柱和高窗各自建立 `Mesh`，并各自提交 draw call。经具体源码审计，这些对象没有被玩法、动画、相机跟踪或物件查询按名称动态引用；已有的看台座椅本身已用 `InstancedMesh` 合批，不重复改造。

只在明确 `?qa=1&r161StadiumBatch=on` 时：
1. 按固定名称前缀归集 **53 个实际静态 Mesh → 5 个 InstancedMesh**，理论最多节省48个draw calls；
2. 每组严查原对象 `BoxGeometry.parameters`、PBR 颜色/发光/金属度/粗糙度/透明度、阴影及相机层完全一致；
3. 原 Mesh 的 **全部16维 transform matrix** 原样写入对应 instance buffer，并逐维校验误差不超过1e-6。总计53个矩阵验证通过；
4. 保留原材质对象与几何原件的 GPU 表示供新 InstancedMesh 使用，其余重复资源仅在确认可释放时释放；
5. 完整体育馆其他几何、座椅、人物、召唤、特效和动态材质保持原实现；
6. `r161StadiumBatch=off` 或非 QA 保留原站原始场景，无公开默认变化。

## 双相机性能归因

`scene/scene.mjs` 仅 QA 开启 `r161Profile=on` 时统计：
- 主竞技场 WebGLRenderer.render 调用周围的 CPU 提交时间；
- 举牌人像（R124 inset）独立 WebGLRenderer.render 的 CPU 提交时间；
- 两者各自的实际 `renderer.info.render.calls`；
- 最多240帧样本，以免无限累积；
- `?qa=1&r161Inset=off` 仅用于归因：**会改变视觉内容，不能作为正式零画质损失优化发布**。

特别注意，`performance.now()` 围绕 `renderer.render()` 测到的是浏览器 JavaScript → WebGL 提交的 CPU 时间（可能包含 driver stall），并**不是实际 GPU 耗时**。后续如需 GPU 时间必须使用可靠 GPU timer queries / profiler。

## 第一轮真实 Chrome Vulkan 结果（桌面1280×720，CPU限速2倍）

| 组别 | 主竞技场draw calls 中位数 | 人像额外draw calls中位数 | 主render CPU提交p50 | 人像CPU提交p50 |
|--|--:|--:|--:|--:|
| 原版 + 人像 | 935 | 128 | 12.6ms | 2.7ms |
| 静态合批 + 同一人像 | **912** | **128** | 12.3ms | 2.1ms |
| 诊断：原版静态物件 + 人像关闭（QA only） | 935 | 0 | 10.8ms | 0ms |

*数据来自单轮完整的实际Chrome受限测试。样本中存在单次高I/O停顿，不能因 p50 降0.3ms就宣布持续性能改善。人像关闭方案因为减少可见内容，因此不能作为正式优化。*

首轮三组均验证 16/16 真实模型、60张卡、T01/E03两个实际模型召唤及攻击、R147原安全镜头、0 HTTP/JS 错误。

静态画面对照中，上部裁剪区域 RGB 每通道平均绝对差小于0.003/255，右上静态区域逐像素相同；整帧因不同采样时刻的人物动画而有少量差异，不能混淆为静态物件质量差异。

**实际 draw calls 中位数减少23，而非宣称固定减少48**：静态物件本身存在视锥剔除与不同阶段开销。

## 决策与待完成

- 优化仍保持 QA-only，等待桌面反向复核、手机模拟、CI检查与完整视觉验收；
- 出牌人像独立约128次 draw calls和2–3ms CPU提交，今后研究缓存常量投影矩阵、减少重复骨骼查找、WebGL2 GPU计时与合理批处理，但**不删除对手反馈或人物表现**；
- 若静态批处理没有稳定 FPS 收益，也保留证据，不能用“48个物件合并”代替真实性能报告；
- 低端手机的真实 GPU、内存、耗电和帧时间尚未验收，模拟视口并不等于真机。

## 全部验收已完成：9/9 Chrome 场景通过

桌面1280×720（CPU×2）和手机模拟430×900 DPR2（CPU×3），正序与反序独立 context/无 SW 缓存；再加只供归因的“人像关闭”1组，共9组，全部通过：
- 真实原始R147模型 **16/16**，12种召唤、60卡牌、T01/E03双单位入场、实际伤害事件，以及原R147安全镜头；
- 全部网络模型下载字节 **75,569,762 B** 原封不动；零浏览器 JS/HTTP 错误；
- 合批后的53个静态物件在5个实例组内，材质/阴影/几何参数和16维变换矩阵全部一致；
- 本轮没有修改任何原有卡牌、单位模型、法线贴图、美术图案或贴图分辨率；
- 所有数据记录于 `qa/evidence/r161-stadium/r161-final-summary.json`，并附4份完整Chrome结果和4张真实浏览器截图。

| 视口/顺序 | 原版主场景draw p50 | 合批版主场景draw p50 | 实际减少 | 原版举牌p95 | 合批版举牌p95 |
|--|--:|--:|--:|--:|--:|
| 1280正序 | 935 | 912 | 23 | 33.4ms | 33.4ms |

| 430正序 | 930 | 891 | 39 | 50.0ms | 50.0ms |

- **真实 draw calls 减少是稳定的；举牌阶段 FPS/卡顿尚未改善**，不能宣称完成主要性能目标。
- 举牌人像固定约128额外draw calls，桌面CPU提交p50约2.1–2.7ms，手机模拟约2.8–3.1ms（不是GPU真实耗时）；关闭人像诊断会改变画面内容，绝不作为可默认上线的“无损”优化。
- 静态区域视觉比较在不同测试批次中RGB均值差异很低（小于0.025/255/通道），但异步动画使整帧无法同步逐像素比对，不应宣称整体画面像素完全相同。真正的材料/位置一致性由源代码逐项硬断言保障。
- 对照图 `qa/evidence/r161-stadium/r161-baseline-vs-instanced-chrome.jpg`；矩阵、渲染测量等机器回执同目录。
- Chrome手机视口和CPU限速不是 Android 真机验证，CI workflow和玩家操作还需要另外验收。

## 综合决策

**继续 Draft、不合并、不发布。** 允许继续研发以不改变美术、动作、特效为前提的 draw-call 优化，但这个工作包还不值得直接对用户宣称“手机战斗不卡了”。下一优先工作应将GPU计时器与 Chrome trace 联合起来，确定主角色表面数量、骨骼更新、阴影通道、R124人像二次render 哪个才是卡帧的主因；对可视内容有损的减少一律不得默认应用。
