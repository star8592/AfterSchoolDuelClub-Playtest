# R167｜魔法光源槽位到底能不能消除首次发招卡顿

2026-11-18；《放学后决斗社》**Web** 版 Z890 Chrome/Vulkan 本地隔离实验。基于前置 R166 首发 Shader 问题调查。状态：**质量/功能通过，性能 NO-GO，Draft、不发布**。

## 为什么需要这轮

R166 发现真实E06施法使体育馆点光源从4盏增加到6盏，伴随约62个WebGL程序变体首次创建。直接调用 `renderer.compile` 对点光源组合预热，耗费约58ms阻塞，未稳定消除施法长帧。

Three.js 的灯光计算依赖 `scene.traverseVisible`，**强度为0但仍可见的点光源仍参与灯光 Shader 宏统计**。预留固定光源槽位可以减少每次施法时Shader编译；反过来，即使光源从未亮起，所有材质的照明程序也会变大、待机GPU可能受到影响。因此本轮**直接测量这一取舍**。

## 实现（只在QA内）

- `r167-spell-light-slots.mjs` 为真实`THREE.PointLight`提供2或4个对象槽位。闲置时强度严格0；发招时从共享池申领，精确保持原光源位置、颜色、强度、照射距离、衰减指数和跟随父节点的动画轨迹；结束后恢复闲置对象，不删除角色、粒子或命中动画。
- 接入4个实际施法模块：`spell-impact`、`magic-arsenal`、`elemental-vfx`、`spell-contact-fx`，溢出时仍按原始方法创建灯光，绝不因为性能而省略光照。
- 仅`?qa=1&r167LightSlots=2`或`?qa=1&r167LightSlots=4`启用；不满足QA条件则沿用原R147的逐次创建/销毁。
- 单独提供 `?qa=1&r166ShaderProbe=on&r167GpuBench=on`：查询WebGL2 `EXT_disjoint_timer_query_webgl2`，无 `gl.finish`，仅等`QUERY_RESULT_AVAILABLE`成功时读取上一帧的GPU时间，区分主场景/非阻塞时间。绝不把GPU时间与CPU排队时间混为一谈。
- 记录零强度槽位的待机成本、真实首次及重复施法长任务、Shader程序数、溢出数量、角色原始素材完整性。没有降贴图DPR、简化人物模型或删魔法。

## 本地测量

Z890 RTX 5070Ti Chrome WebGL2/Vulkan，桌面 1280×720 CPU×2、手机视口430×900 DPR2 CPU×3（**不是真实Android硬件**）；三种模式：原版、2槽位、4槽位。4组各两次原E06实战播放，共 5个A/B案例、10次真实施法；16/16真实模型、60/60卡牌和原75,569,762字节模型原封不动。

注意：此表为每个变体**单次受控Chrome实验**，运行顺序不全部平衡、后台负载会变化，待机GPU相差0.09–0.37ms**不能视作稳定加速/减速证明**。数据既没有呈现施法卡顿大幅消失，也没有证明待机光照成本可接受。

- 4槽位每张E06魔法实际同时最多借走3盏，已覆盖该代表魔法；当更多魔法同时施放，池容量仍可能不够，溢出时仍有Shader变更。
- 4槽位使首次Shader程序增量从约65降至3，但首发最长任务保持数百毫秒，意味着Shader变体数量不是该长任务的全部成因；应继续用Chrome Performance trace分辨首次编译、模型/材质初始化、GC、GPU驱动提交等。
- 原场景有其他光源/贴图、人物动画，因此静态截图异步拍摄存在时间差。本轮严格保持素材、PBR参数、实际有效点光源属性不变，**没有宣称整帧像素完全相等**。
- 2槽位明确不足，出现2次溢出。4槽位虽不溢出但会常驻增大着色器排列数/运行时负担。
- 不要用减少灯光、降低角色精度、删特效来掩盖真实问题。

## 验收结果、原始证据与后续

**NO-GO：功能通过，性能目标未达到，不合并、不发布、不默认开启。** 真机Android未测。
