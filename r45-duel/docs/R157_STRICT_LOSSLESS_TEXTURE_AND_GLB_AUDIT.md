# R157 · 只接受真正不降低画质的 Web 纹理与模型优化

日期：2026-11-18。**独立研究分支，Draft，不影响 R147 正式版。**

## 用户质量硬约束

**任何正式优化不得降低图像质量。** 禁止以“缩小分辨率”“肉眼看不太出”替代无损承诺。必须把三类结果分开：

1. **字节级无损**：所有解码后 glTF 字节、网格、骨骼、贴图、材质、动作完全一致。这类变更有数学级别可验证的等价性；
2. **像素级无损**：如图片以不同封装编码，但解码后的 RGBA 每一通道逐像素完全相同；图像展示质量相同，仍须确认颜色空间、纹理通道、透明度及 mipmap 行为；
3. **有损但视觉相近**：下采样/程序化重绘/KTX2 ETC1S、UASTC 等格式往往改变样本或纹理细节，不能宣称无损。只可进入与默认隔离的视觉研究分支，若用户要求“绝不降低画质”，**不应作为正式默认优化**。

注意：运行时程序化 shader 可减少某些纹理的下载，但增加像素/片元计算，弱 GPU 可能掉帧。离线程序化只适合美术设计存在数学规则的表面（木纹、墙面微粒、规律布料），不能在保留既有独特人物相貌和服装图案的同时神奇恢复所有原始像素，除非保留等价信息量。

## 16 个开局角色真实资源审计

- 当前 4 VRM + 12 GLB 首次模型接收量 **75,569,762 B**；
- 模型内嵌 **136 张图片**，普通 glTF 材质直接引用的图片字节约 **38,604,155 B**。这个统计是**图片嵌入大小**，不是另行累计 HTTP 下载，更不是 GPU 显存；
- 标准 glTF 未引用图片约 **5,367,190 B**，其中此前 R155 已单独剔除的四张 VRM 封面 Thumbnail 为 **5,173,272 B**。VRM MToon、扩展数据或其他非标准用途可能引用部分其余图片，**不能根据普通 glTF 标准引用追踪再直接删除**；
- 发现 **21 组图片内容 SHA-256 完全重复**，重复编码字节总计约 **1,094,500 B**，其中被标准材质引用的重复部分约 **997,196 B**。绝大多数是不同 VRM 文件间的重用，需要调整 glTF 扩展/网络资源引用和 Three.js 加载才能跨模型去重，存在额外网络请求/兼容性成本，不能声称当前已节省；
- 体积较大的纹理主要为 T01 的两张羽毛法线（3.88MB 和 2.70MB）与 T01 基础色、G02 裤鞋、T03 牛仔裤与四个 VRM 人物的身体法线/服装图案等。**这些正在被渲染，不能删除或简单降清晰度**；
- 部分 3D 角色根本没有内嵌图片，体积来自几何/动画，程序化贴图并不适用；
- 体育馆有一套真实 PBR 地板色彩、法线与粗糙度 JPEG，体积约 2.35 MB。这些图片是外部资产，不含于模型接收量 75.57MB。当前运行材质已有高清纹理，程序化替换需审美验收，不能以无损论证。

## 图片逐像素精确重编码实验

以 Pillow WebP lossless（保留全部像素与尺寸）抽测14张大图：

- 多张 WebP 重新无损编码**反而更大**：例如 T01 3.88MB 羽毛法线→4.15MB，T01 0.78MB 羽毛色彩图→0.83MB；
- 个别完全相同的 RGBA/RGB 图片减小了少量：T01 1.44MB 身体色彩图省 9,386 B，G02 鞋子省 7,632 B，VRM 单张身体法线可省 66,896 B，服装图小幅减少；
- 这说明许多原始图片本就高度压缩，**任何重新编码都必须在“逐像素精确相等 + 最终二进制真变小 + 浏览器一致性”下筛选**；不能只追求格式转换。

## R157 完成的真正严格无损改造

只对开局真实使用的 **12 个官方 .glb.gz 资源**进行 gzip 压缩等级提高和确定性重编码：
- 12 个原始 `.glb` 文件、模型内容及原始图片数据**全部原封不动**；
- 原 12 个 gzip 总计 **44,902,902 B**，新 **44,202,314 B**，减少 **700,588 B**（仅这一组占1.56%，全16模型占0.927%）；
- 每一项都验证 `gzip.decompress(原压缩包) == gzip.decompress(新压缩包) == 原始.glb`，因此 **glTF 原始字节逐字节一致**；
- R125 资产指纹依据新压缩包 SHA-256 全部更新。防止浏览器用旧压缩包搭配新缓存 digest；
- 源代码生成器：`qa/repack-r157-strict-lossless-gzip.py`；机器可读回执：`qa/evidence/r157-strict-lossless/repack.json`；
- Chrome Vulkan（Z890）真正执行桌面 **1280×720@1**、手机模拟视口 **430×900@2**，基线→优化和优化→基线两轮：16/16 真实加载，60 卡牌，T01+E03 双角色战斗事件，R147 原摄像机保护，16项缓存、0 JS/HTTP 报错全部通过。优化版读取总字节 **74,869,174 B**（原版75,569,762 B），完整回执见相同 evidence 目录；
- 测试是 Z890 模拟手机视口，**并非低端手机真机**；小幅启动秒数差异受浏览器/SSD 缓存波动影响，不能宣称稳定速度改善百分比。

## 关于先前 R156 的地位

R156 猫头鹰两张法线做了 2048→1024/512 混合程序化，**它是有损图像表示**，虽然浏览器画面表现接近、Chrome A/B通过，仍然改变原始法线像素和纹理细节。既然最新要求是画质不能降低，它**不能合并为正式默认素材**。保留在单独的 R154–R156 Draft 研究分支，不应与本严格无损 PR 互相污染。

## 后续只做符合质量门槛的方向

1. 优先验证高重复度图片是否能够在**同一 GLB 内**仅保留一个 bufferView，并确保所有材质引用/纹理状态不变；跨 VRM 复用须独立验证缓存与 VRM 插件 MToon 兼容。
2. 同一贴图的真正无损重编码：尺寸、精确 RGBA、色彩空间、mipmap、材质参数全部一致，收益小于风险/运维成本时直接跳过。
3. 评估 GPU 可无损显示的替代路径时不能仅根据“看起来差不多”验收，KTX2/Basis 通常为 GPU 压缩格式，视觉近似但多数为有损，不能因为文件名是 KTX2 就视作严格无损。
4. **优化加载调度/网络并发、缓存回填、惰性加载 UI 与动画主线程**，能不改动模型图片就改善首屏体验，是更符合“零画质损失”的长期主线。
5. 必须避免页面级缓存跨版本错配，并持续保留 R147 贴图与镜头安全回退。

**此 PR 只验证“画质完全没变化且资源变小”这一可证明目标；在低端真机、CI 全量回归等未完成前保持 Draft。**
