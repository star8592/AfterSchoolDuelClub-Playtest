# R125 · 16 个真实三维模型的内容指纹与本机持久缓存

日期：2026-11-13。基线 `main 13f2920` 已包括 R121/122/123、R124 实际人物表情、真人口型、看台误伤、广播与无损 GLB 压缩。

## 明确的问题

正式 GitHub Pages 在 2026-11-13 Z890 单次浏览器测得完整模型传输 75,569,762 字节（约 72.07 MiB），真实公网冷就绪样本约 47.6–58.2 秒；开发机本地服务约 2.5 秒。后者不代表新用户公网加载。

四个真实 VRM 共 29.246 MiB，GZIP-9 压缩后为 27.257 MiB（只减少 1.989 MiB、6.8%），故本次不增加 4 份大型 VRM .gz，更不能更换低模人物。Chrome 当前不具备普遍可用的原生 DecompressionStream('brotli')，没有冒险把全站强切 Brotli。

GitHub Pages 当前实际 VRM 和 .glb.gz 资源 HTTP 响应 `Cache-Control: max-age=600`。这意味着复玩时不应只依靠 10 分钟 HTTP 缓存。

## 精确改动

- 为 4 个真正源 VRM 和 12 个已无损 GZIP 的真实 GLB 传输文件编制完整 SHA-256 指纹，集中于 `r45-duel/r125-asset-fingerprints.js`。
- 游戏读取这些资源时只附加对应内容指纹的 `?v=<SHA256 前16位>`。**只增加资源 URL 标识，不改变文件内容、GLTFLoader、动作、材质或玩法**；旧模型不可能用旧指纹 URL 冒充新版。
- 同源、专用 Service Worker 注册范围仅为 `r45-duel/`。它只拦截上述 16 个**精确路径 + 当前指纹**的 GET 请求；不缓存任何 HTML、JS、规则、支付、用户数据、页面或其他站点内容。
- 响应首先直接交给原始场景流式解析，缓存写入不阻塞真实就绪。首次注册的页面若因 SW 启动较晚没缓存齐，则等场景已经证明 16/16 真实模型就绪后在空闲时间从浏览器 HTTP 缓存回填最多 16 项，两个任务有界并发。仅在浏览器具备足够可用存储且用户未开启节省流量时主动回填。
- 资源更换必须同步更新指纹；Worker 激活时清理指纹不匹配的旧项，**没有旧模型混搭**。只有这 16 项属于缓存；其余旧研究模型和 `?r124Packed=off` 原文件保持网络原有路径。
- `?r125Cache=off` 显式关闭指纹缓存；不支持 Service Worker 的设备自动按 R124 正常加载。Worker 缓存写入失败也不能把模型伪装成加载成功。

### 受控下载带宽实验

在 Z890 对**全体模型下载**而非仅页面顶层网络启用独立 Python ThreadingHTTPServer 共享带宽限制（2 MiB/s，HTTP Cache-Control max-age=3600），Chrome 冷启动首次实际验证 16 模型、再用同一浏览器配置重新进入：**37,559 ms → 2,416 ms（约 15.55 倍）**；两次都实际确认 16/16 模型、12 召唤来源存在。该数字为特定实验室带宽模拟，**不能当作真实公网某地区的代表性结果**。

另一次 Chrome CDP 网络限制未有效约束同源 iframe 的资源请求，其数据**不计作有效带宽基准**。

## 事实边界与后续

本轮主要是**重复访问性能**，首次纯冷加载没有因缓存自动消除 72 MiB 下载。当前严格保留“16/16 全部真实模型后才允许出牌”的游戏就绪条件，以免未就绪人物造成白模/低模/T pose 与规则结算抢跑。冷启动的后续阶段应该单独研究按卡组、有实际演出时序保障的安全渐进加载。

部署以前必须检查：main 合并回执、Pages 构建/发布 SHA、公网真机浏览器首次/第二次访问、SW scope 及 16 项命中。不能只用本地 QA 声称已经上线。
